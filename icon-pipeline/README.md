# icon-pipeline — 企业级 icon/UI 资产工作流（L4→L6 脊柱已量化）

ComfyUI 跑在 WSL 发行版 `ComfyUI`（`/data/ComfyUI`，RTX 4080 SUPER 16GB）。本目录只做脊柱与门禁；生成端（L1–L3）尚未接入。

## 怎么用

```bash
# WSL 内，全部离线可跑（不需外网）
cd /mnt/h/workflow/icon-pipeline
bash run_all.sh                      # 矢量化 4 档 → 门禁 → 规范 → 复量 → 尺子自检
PY=/data/ComfyUI/venv/bin/python

$PY tools/qa_gate.py --dir run/svg/polygon          # 逐资产对照表
$PY tools/qa_gate.py --selftest --source run/gt/gear_gt.png --svg run/svg/polygon/gear.svg
$PY tools/svg_norm.py --dir run/svg/polygon         # viewBox + 居中留白 + transform 烘焙
$PY tools/synth_icons.py brand-kit.example.json run/gt   # 重建真值测试图
```

改阈值/色板/栅格只改 `brand-kit.example.json`，脚本与门禁都读它。

## 已量化结论

真值：6 个合成扁平图标（颜色精确取自 palette，alpha 仅 0/255）。

矢量化参数对照（6 资产合计路径节点数 / 最差形状偏差 / 规范后总体积）：

| preset | 节点 | max chamfer（24px 栅格单位） | max rmse | 规范后 bytes |
|---|---|---|---|---|
| tight | 693 | 0.104 | 5.48 | 31303 |
| default | 512 | 0.063 | 3.37 | 23118 |
| coarse | 338 | 0.101 | 2.36 | 13941 |
| **polygon** | **458** | **0.059** | **3.37** | **4859** |

- `polygon` 在保真与体积上同时最优：节点比 tight 少 34%，最差 chamfer 好 1.8 倍，文件小 6.4 倍。
- `coarse` 节点最少但在 shield 上有保真悬崖（0.101 vs polygon 同资产 0.046）——省节点不是免费的。
- 形状保真本身极好：**24px 图标上轮廓平均偏差 0.05–0.10px**，色值 ΔE=0（palette 精确命中），16px 缩略 SSIM ≥0.994。
- 规范前 0/6 PASS，失败项**全是布局**（fill 0.596–0.822 vs 目标 0.88、bbox 偏移最高 6.25%）；`svg_norm` 后四档一致 **6/6 PASS，修复 2、回归 0**。
- 烘焙 `translate` 进路径坐标是无损的：chamfer 变化 ≤0.005、IoU 变化 ≤0.008。

## 指标分两层（这是本设计的关键）

- **形状保真**：先按内容外接框配准（`crop_to_bbox_fill`），再算 chamfer / hausdorff p95 / alpha IoU / interior rmse / 16px SSIM。
- **布局合规**：在交付画布自身坐标系里量 bbox 居中偏移、fill 占比、四角 alpha、forbidden 标签、路径/节点/色数预算。

`--selftest` 用 6 种定向扰动断言：每个扰动**只**推动它那一轴的指标，其他轴必须不动。当前两个资产上 16/16 全绿、轴正交。

## 已在真图上的实测（4 张满幅模型出图，非图标域）

L4→L5 端到端跑通：单张 **5.0s**（BiRefNet General + vtracer polygon + 4x 放大分支）。

| 变体 | paths | 色数 | IoU | chamfer | ssim16 | fill |
|---|---|---|---|---|---|---|
| 直接矢量化 | 512–2030 | 302–1753 | 0.84–0.96 | 0.088–0.37 | 0.83–0.98 | 0.94–1.0 |
| `TS_ImageQuantize(colors=4)` 后矢量化 | 38–489 | 24–236 | 0.15–0.62 | 1.67–4.30 | **-0.06–0.21** | 1.0 |

两个结论，都是量出来的不是推的：

1. **量化放在 vtracer 之前是错的插入点。** 它没把色数压到 4（SVG 仍有 24–236 种填充），并且把 alpha 连背景一起量化掉——IoU 从 0.84 崩到 0.15，`fill` 变成 1.0（整幅不透明）。控制色数该用 vtracer 自己的 `color_precision`/`layer_difference`，或量化时必须保 alpha。
2. 照片域素材被门禁全判死是**正确行为**，不是流水线故障。

过程中修掉两个我自己的度量装置 bug：`svg_norm` 用 512 栅格坐标去写原生单位（真图原生 1024）的 viewBox 尺度错——合成集是正方 512 恰好掩盖了它；以及脊柱里 vtracer 与对照栅格不同帧（一个吃 1024 原图、一个吃 center-crop 512），导致 IoU 假性低到 0.45。

## 真图标集实测（8 张 Z-Image int8 生成，L1→L6 全链路）

生成 4.0s/张（首张 118s 含权重加载）；脊柱 5.0s/张。形状保真：

| 指标 | 合成图标 | 真图标（8 张） | 预算 | 结论 |
|---|---|---|---|---|
| chamfer | 0.046–0.059 | **0.063–0.109** | ≤0.12 | **达标，不用重标** |
| hausdorff p95 | 0.045–0.09 | 0.128–0.269 | ≤0.9 | 达标 |
| interior rmse | 0–5.5 | 3.1–23.4 | ≤10 | 2 张超 |
| ssim16 | ≥0.994 | 0.954–0.998 | ≥0.95 | 达标 |
| alpha IoU | 0.985–0.997 | 0.880–0.986 | ≥0.97 | **3/8 被拒** |
| paths | 1–3 | **138–832** | ≤16 | 超 8.6–52 倍 |
| 色数 | 1–3 | **63–139** | ≤4 | 超 16–35 倍 |
| 最大 ΔE | 0 | 50.9–86.8 | ≤3.0 | 全超 |

三条结论：

1. **`max_chamfer_grid_px=0.12` 不需要为重标**——真图标最差 0.109，且比合成集只差 1.5–1.8 倍。软边并没有把它推爆。
2. **真正的瓶颈不是矢量化器，是"扁平化"这一层缺失。** Z-Image 出的是带抗锯齿渐变的位图，vtracer 忠实地给出几百条路径。要入库必须加一步**保 alpha 的调色板归约**（矢量侧：把 fill 吸附到 brand palette、同色路径合并、丢弃碎小路径），一次同时压掉 paths / 色数 / ΔE 三项。
3. `svg_norm` 在真资产上确认无损且更省：`bboxOff 0.98–2.93 → 0.2–0.39`、`fill → 0.88`、chamfer 变化 ≤0.006、IoU 变化 ≤0.003，**体积反而降 25–32%**（如 62051→42137）。

未定：IoU 拒掉的 3 张（0.880/0.939/0.956）成因还没查。低 `fill` 不是解释——hex_badge fill 0.70 却是最差的 0.880，而 folder fill 0.645 有 0.939，不单调。需要看剪影差异图才能定，不猜。

## L5.6 矢量侧调色板归约（`tools/svg_flat.py`）

在 `svg_norm` 之后跑（路径已是绝对用户单位、无 per-path transform）。三个开关独立，因为各自换掉的是不同的东西：`--snap`（fill 吸附 brand palette）、`--group`（同色路径合并为一条多子路径）、`--min-area`（丢碎小路径，按 bbox 面积，对曲线路径会**高估**因而保守）。

8 张真图标 before/after：

| 指标 | before | after | 预算 |
|---|---|---|---|
| paths | 138–832 | **3–5** | ≤16 ✓ |
| 色数 | 63–139 | **3–5** | ≤4（2 张 5 色） |
| max ΔE | 50.9–86.8 | **0.0** | ≤3.0 ✓ |
| chamfer | 0.064–0.110 | **完全不变** | ≤0.12 ✓ |
| alpha IoU | 0.879–0.985 | **完全不变** | ≥0.97 |
| path_nodes | 715–2952 | **不变** | ≤260 ✗ |

三条结论：

1. **归约是几何无损的**：chamfer / IoU 前后小数点后三位都没动。我事先担心的"`--group` 重排 stacking 可能破坏遮挡"**实测没有发生**。paths 降 60–200 倍的代价是零。
2. **上一轮"rmse 炸了"是我读错了。** `interior_rmse` 拿矢量去逐像素比对**那张带渐变的源位图**，于是它在惩罚我们有意做的扁平化。加上正确的对照（`interior_rmse_vs_snapped`：先把源图自身颜色吸附到调色板再比）后，**8 张里有 7 张归约后反而变好**（arrow 8.7→2.8、gear 42.4→11.8、folder 58.1→24.9）。
3. **唯一例外才是真信号**：`hex_badge` 在对照口径下反而恶化（40.1→63.2），而它正是层数最多的那张（832 paths / 2952 nodes），IoU 也本来就最差 0.879。说明**扁平化必须在生成端就成立，不能全靠事后归约救** —— 层数越多的源，事后压平丢的结构越多。

剩下唯一的硬性预算缺口是 `path_nodes`（715–2952 vs 260），合并路径不减命令数，这是**另一个杠杆**：vtracer 的 `length_threshold`/`max_iterations`，或 `TS_SVGPathSimplify`。

## path_nodes 参数扫描：负结果（`tools/sweep_nodes.py`）

评的是最终交付文件（矢量化 → `svg_norm` → `svg_flat` → 门禁），不是中间态。18 档 × 8 张。

**结论：vtracer 的参数不是节点数的杠杆。**

| 扫的参数 | 范围 | 对 nodes max 的影响 |
|---|---|---|
| `length_threshold`（polygon） | 4 → 50 | **0**，输出逐字节相同（均 2952 / 73543B） |
| `filter_speckle` | 4 → 30 | 2952 → 2919（1.1%） |
| `corner_threshold`（spline） | 40 → 90 | 2433 → 2473（1.6%），且 ct40 使 chamfer 恶化到 0.428 |

机制解释：节点数由源图**等色带轮廓的条数与长度**决定（抗锯齿渐变 → 大量长轮廓），而上述参数只做碎点剔除和拐角判定，触及不到主体轮廓的顶点密度。

附带两条：

- `ssim16 min`（0.774）与 `rmseS`（63.2）在 **18 档里数值完全不变** —— 这两项卡在调色板塌陷上，与几何参数无关。
- `nodes max` 恒由层数最多的 `hex_badge` 决定（中位数仅 985），与 L5.6 的结论同源：源越厚，事后越救不回。
- `col 5` 超 `max_colors=4` 的原因是 palette 有 6 个 token、吸附后自然用上 5 个色 —— 属配色规范问题，不是矢量化器问题。

**`TS_SVGPathSimplify` 不可用（`tools/sweep_simplify.py`）**：tol 0.5→40、两种图位（grouping 前 / 后）都试了。
norm 阶段基线 chamfer 0.064–0.110 / IoU 0.879–0.985 / SSIM16 ≥0.95，在 **tol=0.5 时就已变成 chamfer 0.810 / IoU 0.572 / SSIM16 0.232**，
之后整条曲线与容差无关（0.810, 0.824, 0.829, 0.832, 0.832, 0.830, 0.819, 0.845, 0.764）。
0.5 个 viewBox 单位 = **0.027 栅格像素**，几何上等于不动，所以这不是简化损失而是**结构损伤**：
`extract_points_from_path` 把所有命令拍平成一个点列，曲线退化为顶点、子路径结构丢失。
它会砍顶点（grouped 输入上 2952→307），所以文件变小、图形却是错的。换图位不能修，损伤是固有的。

## 自建 RDP 简化器（`tools/svg_rdp.py`）：实现正确，但补不上 `path_nodes`

两条硬约束是照着 `TS_SVGPathSimplify` 的病写的，且都在运行时断言：按 `M…Z` **逐子路径**独立简化（绝不跨岛/跨洞连接）；路径里出现 M/L/Z 以外的命令就 **raise**，不偷偷把贝塞尔转成顶点。

**eps=0 控制组通过**：逐张 chamfer 与 `_flat` 基线完全相等（0.081/0.102/0.092/0.110/0.064/0.094/0.079/0.079），IoU 同样逐张相等，顶点仅 754→752（丢严格共线点）。所以这套实现是无损的。

交换曲线（8 张取最差/中位）：

| eps | 0 | 1 | 2 | 3 | 4 | 6 | 10 |
|---|---|---|---|---|---|---|---|
| nodes max | 2946 | 2774 | 2720 | **2101** | 2082 | 2056 | 2034 |
| nodes med | 1144 | 1054 | 968 | 900 | 882 | 853 | 826 |
| cham max | 0.110 | 0.099 | 0.099 | **0.098** | 0.115 | 0.134 ✗ | 0.187 ✗ |

**结论：260 的节点预算不可能靠后处理达成。** 拐点在 eps≈3（降 29%，chamfer 还略好，因为抖点被去掉），但之后 RDP 封顶在 ~2030 —— 而从 2946 到 260 需要 11 倍。物理原因清楚：`paths` 经 flat 后只剩 3–5 条，节点全部堆在**少数几条极长的等色带轮廓**上；RDP 只能削单条轮廓内部的冗余顶点，削不动"轮廓有多少条"，而后者由源图色带数量决定。

另一个约束值得单独记：**chamfer 预算的余量只有 0.010 栅格像素 ≈ 0.2 个 viewBox 单位**，所以可花在简化上的容差本来就近乎为零。

因此 `path_nodes` 只剩两个站得住的出路：**在生成端减少等色带**（扁平出图，治因），或**把预算重新定为有测量依据的数**（260 是我最开始拍的，从未论证）。当前实测分布：eps=3 时中位 900、最差 2101，且最差值由层数最多的 `hex_badge` 独占。

## 3D 线：Hunyuan3D 2.1 端到端已跑通（`workflows/3d_*.json`、`tools/mesh_stats.py`）

零下载：`ImageOnlyCheckpointLoader(hunyuan_3d_v2.1.safetensors)` 一次给 MODEL / CLIP_VISION / VAE，
链路 `CLIPVisionEncode → Hunyuan3Dv2Conditioning → EmptyLatentHunyuan3Dv2(4096) → KSampler(30/5/euler/normal)
→ VAEDecodeHunyuan3D(8000, octree 256) → VoxelToMesh(surface net, 0.6)`，后处理接
`DecimateMesh → WeldVertices → FillHoles → MeshSmoothNormals → UnwrapMesh → SaveGLB / RenderMesh`。

冷跑（换 seed 强制整链重算）：**39.7s**，`peak mem_used 15805 MiB`、`min avail 58 MiB`（配额 15863）、`peak gpu 11097 MiB`。

| | 原始网格 | 后处理后 |
|---|---|---|
| 三角面 | 1,205,010 | **3,385** |
| 顶点 | 382,787 | 2,823 |
| 属性 | POSITION | POSITION + TEXCOORD_0 |
| 法线 | 无 | **仍无**（`MeshSmoothNormals` 未落盘） |
| 包围盒 | 1.96×1.78×1.95 | 1.85×1.40×1.82（未归一） |
| 文件 | 19.06 MB | 0.10 MB |

三条实测结论：

1. **内存峰值由生成段决定，后处理顺序改不动它。** 我曾假设"先降面再处理"能压低峰值——冷跑证伪：15805 vs 纯生成 15595，几乎相同。峰值来自 `VAEDecodeHunyuan3D(octree 256)` + `VoxelToMesh`，120 万面必须先存在。58 MiB 的余量就是这台机器跑 3D 的现状，**贴着 WSL 上限**。
2. `target_face_count=20000` 实得 **3385 面**（低于目标 5.9 倍）——`DecimateMesh` 的 target 语义不是"降到目标即停"，因此不能用它设面数预算。
3. UV 出来了但 `NORMAL` 没进 GLB；包围盒未归一到 1 单位，且**没有现成节点做缩放归一**（只有 `RotateMesh`）。

`mesh_stats.py` 直接解析 GLB 的 JSON chunk，不需要 3D 库——注意它第一版把属性名按 `_` 截断，`TEXCOORD_0` 显示成 `'0'`，差点导致"UV 没生成"的误判，已修。

## 密度—保真—内存（`tools/sweep_octree.sh`，固定 latent 4096 + 固定 seed，只动 octree_resolution）

| octree | peak mem | 余量 | raw 三角面 | 剪影 IoU vs 256 | cham px(/512) |
|---|---|---|---|---|---|
| 128 | 11652 MiB | **4210 MiB** | 265,354 | 0.9042 | 3.32 |
| 192 | 13062 MiB | 2801 MiB | 645,320 | 0.9211 | 2.99 |
| 256 | 15773 MiB | **89 MiB** | 1,205,010 | — | — |

结论：**内存峰值由 `octree_resolution` 单调决定**，与后处理顺序无关。256→128 用 4.6 倍更少的原始面和 0.65% 画面宽的剪影偏差，换回 4.1 GiB 余量。**3D 线不需要提 WSL 内存**；128/192 档即可安全重复。计时本轮不可信（KSampler/VAE 命中缓存）。

两次实验方法学教训（都记进项目记忆）：
1. `EmptyLatentHunyuan3Dv2.resolution` 是**潜变量尺寸不是画质档** —— 同 seed 换它 = 换物体。第一版三档对照因此全废（192 对 256 的 IoU 反而比 128 更差，非单调即其信号）。
2. 剪影**不能从 solid 着色渲染的 RGB 用亮度阈值反推** —— 暗面会被算作背景，量到的是光照不是几何（第一版给出 0.71 的假非单调）。必须接 `RenderMesh` 的 **MASK 输出**；接上后立刻单调。

## D0 输入规范已被证明是 3D 线的决定性变量

真值尺子先自校：`tools/make_solid.py` 写出解析 UV 球 GLB，`tools/mesh_metrics.py` 在它上面给出
1 壳 / 0 开口边 / 0 非流形 / thinness **4.8**（解析值 4.836）、体积误差 0.27% —— 度量可信。

同一套度量对着两种输入：

| | 照片输入 `test.jpg` | 干净合成球体 | 干净两段雪人 |
|---|---|---|---|
| 壳数 | **323** | **1** | **2**（= 部件数） |
| 开口边 | 303 | 0 | 0 |
| 非流形边 | 535,932（≈44%） | 54（0.011%） | 66 |
| 最大壳 thinness | **355,101** | 4.8 | 4.8 / 4.8 |

**Hunyuan3D 2.1 本身没问题，323 个壳全是输入图的锅**（光环、两块全息屏、地面反射都被重建成了几何体）。
干净球体的重建精度：体积 3.709 vs 同直径解析球 3.793（**−2.2%**），面积 11.592 vs 11.76（**−1.4%**）。

因此 D0 是硬前置：**单主体、平坦无阴影背景、无悬浮环状物、无地面反射**。icon 线已有的 BiRefNet 抠图阶段正好就是它需要的东西 —— 两条线在此合流。

`thinness = area / volume^(2/3)` 是这里的关键判别量：闭合凸体约 4.8，而"面积巨大、体积近零"的碎面壳能到 10⁵ 量级，
差四五个数量级。剪影 IoU 对这类缺陷完全不敏感（碎面就在轮廓里面）——这是"同一套坏流水线各档位互相比对
只能证明可重复、不能证明正确"的现场版本。

## 缺点 / 未解

1. `path_nodes` 未达标：实测 715–2952 vs 预算 260。vtracer 参数、`TS_SVGPathSimplify`、自建 RDP 三条路均已量化证伪，未决。
2. `interior_rmse` 仍在门禁里且仍按"比对原始渐变源"判定 —— 已加对照列，但没改判定，改判定要单独决定。
3. 生成端未强制扁平（无扁平风格 LoRA），post-hoc 归约对高层数源会丢结构（hex_badge 实测）。
4. IoU 拒收 3/8 的成因未定。低 `fill` 不是解释（hex fill 0.70 → IoU 0.880；folder fill 0.645 → 0.939，不单调）。
5. UI 界面稿那一支需要 Qwen-Image-Edit 底模，当前未下载（P1）。
6. `stacked` 层级下"丢一层路径"可能不改变轮廓（下层补上），所以该缺陷靠 `paths`+`thumb_ssim` 而非 IoU 捕获——已在自检断言里注明。
7. 无 API key，`partner/*` 云端矢量节点全部不可用；矢量只有本地 vtracer/potrace 一条路。
8. WSL 内 pip/apt 均无网，新增 Python 依赖必须 Windows 侧下 wheel 再离线装。
9. WSL 内存被默认限成 15.5 GiB（宿主 31.8GB）且零 swap，权重合计超上限会让整个发行版僵死而非报错。
